# Connectors chain through a shared filesystem sink

The original design had each Connector both detect new content *and* build the Evidence tree itself (`GmailConnector` called the Gmail API and constructed `EvidenceNode`s directly). Adding a second real source (Keep, Drive, ...) would have meant reimplementing tree-building — attachment ordering, `CONTAINED_IN` structure, provenance metadata — from scratch each time, with no reuse between sources.

We're splitting that into two roles instead. An **Importer** is source-specific: it knows how to talk to one external API (Gmail, Keep, Drive), owns its own checkpoint against that API, and materializes new content into a shared filesystem sink — one directory per item, a small `_evidence.json` sidecar recording `kind` and `source_ref` (the pointer back to the origin system), and child files as the item's flat attachments. The **Connector** role narrows to exactly one generic implementation, `FilesystemConnector`: it watches the sink, owns its own checkpoint against *the filesystem* (independent of whichever Importer wrote what), and builds the Evidence tree by walking directory structure — nesting and sort order become `CONTAINED_IN` and position for free.

This means every future source only needs a thin Importer (fetch + write files + a sidecar); the tree-building, ordering, and Evidence-writing machinery is built exactly once and shared. We considered keeping the original one-Connector-per-source shape and accepting the duplication, but reuse across N future sources outweighs the cost of one extra indirection layer, and the two checkpoints staying independent (API-side vs filesystem-side) means an Importer's own retry/backoff logic never has to know or care how the Connector consumes what it wrote.
