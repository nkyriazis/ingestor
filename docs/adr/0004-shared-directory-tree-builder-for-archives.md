# Archive expansion reuses the Sink's directory-tree builder

Archives (starting with `.zip`) need the same treatment slide decks already get: unwrapping into individually-addressable Evidence children, cascading through further conversion (a `.pptx` inside a `.zip` still becomes per-slide nodes). The question was where that unwrapping logic should live, and whether it should share code with `FilesystemConnector`, which already turns a directory of files into an Evidence tree when reading the Sink.

We extracted that tree-building logic into `ingestor.directory_tree.build_tree` — a single function that turns any directory into an Evidence tree (sidecar-or-default `kind`, sorted children, recursive subdirectories), used by both `FilesystemConnector` (pointed at the Sink) and `ConvertStep`'s archive expansion (pointed at a temp-extracted copy of the archive). Archive expansion is otherwise ordinary Conversion — it runs inline during `ConvertStep`, not as a separate Sink-writing stage, so there's no new checkpoint or coordination problem between "has this archive been expanded yet" and "has the Connector already read it."

We considered expanding archives at the Sink level instead — a component that watches for archive files and writes their expanded contents back as new Sink entries — but rejected it: it would need its own checkpoint, and `FilesystemConnector` would need to know not to pick up an archive before it's been expanded. Treating an archive as just another content encoding for Convert to unwrap avoids that coordination problem entirely, and reusing `build_tree` means the "walk a directory into an Evidence tree" logic is still written exactly once.
